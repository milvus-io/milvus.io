Milvus gives you four consistency levels — Strong, Bounded, Session, and Eventually — and picking the wrong one is a common source of "my search doesn't see the record I just wrote" bugs. Eventual consistency permits reads to observe an older state while updates propagate. In a retrieval application, a newly inserted passage or a recent correction may not be visible to every read immediately. The consistency policy determines what freshness behavior an application can require; it is separate from whether the data is durably stored.

![Durable write is not yet a visible search result](/images/ai-reference/write-path.svg)

## Connect the policy to the user experience

A user who uploads a document and immediately asks about it may expect read-after-write behavior. An offline recommendation job may tolerate some delay. An application handling access revocation or urgent corrections needs an explicit rule for when old evidence stops being eligible.

Milvus exposes Strong, Bounded, Eventually, and Session consistency levels. Consult the versioned guide for their guarantees and how to configure them. Do not assume that a setting's name alone establishes the requirements of your end-to-end system: application caches, ingestion queues, and source retrieval can introduce additional staleness.

## Measure the trade-off

Stronger freshness requirements can add waiting or coordination to a read path. The practical effect depends on write activity, deployment conditions, and the selected API behavior. Compare latency under realistic concurrent ingestion, not only on a static collection.

Also distinguish retrieval freshness from model freshness. A vector generated by an old embedding model can be fully visible under the chosen consistency level while still being incompatible with the current query encoder.

## Test transitions explicitly

Use a controlled sequence: write a uniquely identifiable record, search for it, update it, then delete it and repeat the read. Record the consistency setting, client/session behavior, and elapsed time. Test error and retry cases as well. Define user-visible handling for indexing in progress and verify that the application meets its stated freshness requirement rather than relying on a single successful demonstration.

## Example to test

After updating a product record, issue a read under the application's intended consistency setting and record when the new revision becomes visible. Check across clients as well as within one session; insertion acknowledgment and searchable visibility are different events.
